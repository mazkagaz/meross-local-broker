# Plan D2.2 — Moteur de profils : chemins, matching, compilation

**Statut** : validé ; D2.2.1 et D2.2.2 implémentés (tests unitaires verts) ;
D2.2.3 à venir.
**Prérequis** : D2.1 (schéma 2, linter) et D2.2.1 (registre).

## Décisions

1. **`type`** : correspondance exacte d’abord, puis plus long préfixe.
2. **Ambiguïté** : meilleur score retenu, avertissement consigné, ordre
   déterministe par id.
3. **Plateformes complexes** : différées en D2.2.3, entité ignorée avec
   avertissement ; le profil reste chargé.
4. **Compilation lazy** au premier appariement, cache par
   `(profile_id, version, hash)`.
5. **Fixtures de test** : copies des profils canoniques dans
   `tests/fixtures/profiles/`, avec contrôle de dérive.

## Périmètre D2.2.2

Inclus :

- `paths.py`, `match.py`, `compiler.py` ;
- compilation des plateformes simples (`cover`, `switch`, `light`, `sensor`,
  `binary_sensor`, `number`, `button`, `select`) ;
- appariement des descripteurs et diagnostics.

Exclus :

- entités HA, polling, commandes réseau (D3) ;
- hubs/sous-appareils et plateformes complexes (D2.2.3) ;
- dispatch runtime des payloads (D2.2.4).

## 1. `profiles/paths.py`

- Grammaire : clés `[A-Za-z0-9_]+` séparées par `.`, index `[n]`.
- `parse_path`, `get_path` (retourne `MISSING`, ne lève pas), `substitute`
  récursif.
- Jetons autorisés : `$channel`, `$value`, remplacement strict (chaîne entière).
- Aucune expression, aucun accès dynamique.

## 2. `profiles/match.py`

Contexte : type, sous-type, MAC normalisée, abilities, `is_hub`.

Score, du plus fort au plus faible :

1. type exact + sous-type exact + MAC ;
2. type exact + sous-type exact ;
3. type exact + abilities ;
4. préfixe de type le plus long ;
5. type générique.

`abilities.all` doit être inclus ; `abilities.any` doit intersecter.
`sub_type` accepte `*`. À score égal : id lexicographique + avertissement.

## 3. `profiles/compiler.py`

- `NamespaceSpec` : méthodes, champs, digest, `PollingSpec`.
- Défauts de polling : `default`, période 60 s, `push=true` si PUSH déclaré,
  `once` si SET seul.
- `EntitySpec` : clé, plateforme, canal, nom, device_class, catégorie, unité,
  état, commandes, quirks.
- Validation des chemins, jetons, namespaces ; erreurs isolées par entité.
- IDs stables préparés pour D3, sans inscription HA.

## 4. Branchement adaptateur

- Après le registre : matching des descripteurs, compilation lazy, cache.
- Diagnostics : `profiles_compiled`, `devices_matched`, `devices_unmatched`,
  `match_ambiguities`, `compile_errors` (bornés).
- Aucune entité, aucun abonnement, aucun poll.

## 5. Séquence

- D2.2.1 (fait) : registre/catalogue.
- D2.2.2 : paths, matching, compilation simple, diagnostics.
- D2.2.3 : hubs, sous-appareils, plateformes complexes.
- D2.2.4 : dispatch runtime des payloads.
- D2.2.5 : interface P3.

## 6. Matrice de tests négatifs (obligatoire)

Chaque cas doit avoir un test dédié, avec l’effet attendu.

### A. Catalogue / registre

| Cas                                       | Attendu                         |
| ----------------------------------------- | ------------------------------- |
| catalogue non-objet, `profiles` non-liste | erreur consignée, registre vide |
| entrée `null`/chaîne, `profile` non-objet | entrée rejetée                  |
| `id`/`version` manquants                  | erreur ou skip                  |
| id dupliqué                               | skip du second, raison          |
| `schema_version` non supporté             | registre non chargé, erreur     |
| `requires_engine` invalide/trop récent    | skip motivé                     |
| `hash` absent ou différent du contenu     | erreur (si vérifié)             |
| révision absente ou incohérente           | avertissement/erreur            |
| erreurs catalogue non-listes              | erreur normalisée               |

### B. Compilation

| Cas                                        | Attendu                        |
| ------------------------------------------ | ------------------------------ |
| plateforme inconnue                        | entité ignorée                 |
| plateforme complexe                        | entité différée, avertissement |
| namespace d’état/commande absent           | entité en erreur               |
| `state.fields` non-objet, chemin vide      | entité en erreur               |
| canal négatif, flottant, booléen           | entité en erreur               |
| jeton inconnu ou partiel                   | entité en erreur               |
| `$value` absent d’une commande qui l’exige | entité en erreur               |
| clé d’entité dupliquée (hub/sous-appareil) | entité en erreur               |
| quirk inconnu ou dupliqué                  | entité en erreur               |
| `device: subdevice` hors template          | entité en erreur               |

### C. Chemins

`a..b`, `.a`, `a.`, `a[`, `a[]`, `a[-1]`, `a[x]`, `a[0][1]`, index sur
scalaire, clé sur liste, profondeur excessive, clé très longue, `__proto__`,
`constructor`, `prototype`, `$` dans une clé.

Attendu : refus du chemin à la compilation ou `MISSING` au runtime ; jamais
d’accès dynamique.

### D. Matching

Aucun match, plusieurs matchs de même score, préfixes qui se chevauchent
(`mss31`/`mss310`), MAC invalide/casse différente, abilities vides.

Attendu : choix déterministe ou non apparié ; ambiguïté signalée.

### E. Runtime (D2.2.4)

Payload non-objet, header absent, namespace inconnu, chemin absent, tableau
trop court, type inattendu, canal hors plage, payload énorme.

Attendu : message ignoré ou erreur isolée, aucun crash d’intégration.

### F. Évolution

`x-*` inconnus conservés, champ cœur inconnu refusé, profils v1 sans champs v2,
valeur d’énumération future (repli moteur), `requires_engine` invalide.

## 7. Tests positifs

- 3 profils canoniques compilés : MRS100 (cover + 2 number + 2 button +
  sensor), mss310 (switch + 3 sensors), msl120 (light).
- Matching type/MAC/abilities ; compilation paresseuse et cache.
- Flag off : comportement actuel inchangé.
- Aucun I/O bloquant.

# MRS100 support in `ha-meross-local-broker` — fork patch

Rather than reimplementing a local Meross stack, this patch extends the
existing add-on. The upstream project already has most of the machinery; the
MRS100 gaps are narrow.

## What already works upstream

- MQTT broker authentication and topics:
  - device client id `fmware:<uuid>_<suffix>` is accepted by the add-on regex;
  - app/device topics `/appliance/<uuid>/publish|subscribe` are relayed;
  - the agent already subscribes to `/appliance/+/subscribe` (app → device).
- HA cover support already exists in `meross-cloud`:
  - `RollerShutterTimerMixin`, `RollerShutterEntityWrapper`,
    `MerossRollerShutterDevice` in `custom_components/meross_cloud/cover.py`;
  - `meross_iot.device_factory` maps the device ability
    `Appliance.RollerShutter.State` to `RollerShutterTimerMixin` and creates a
    dynamic device class with a cover entity.
- The HA manager fetches `Appliance.System.Ability` over MQTT, so the add-on
  does not need to guess the cover class from HTTP metadata.

## Actual MRS100 gaps found

1. **No roller-shutter channel discovery.** `_handle_system_all` only guessed
   channels from `digest.togglex`; MRS100 has no togglex, so the device ended up
   with no channels. HA still defaults to channel 0 in some paths, but the
   broker DB and app-facing `devList` were incomplete.
2. **No persistence of `Appliance.RollerShutter.Config`.** The official cloud
   stores `signalOpen`/`signalClose` and re-applies them; the local add-on did
   not. This matches the reported behavior where values set via HA/`meross_lan`
   fall back to the 50 s default after a reconnect/poll.
3. **Abilities were not cached** in the add-on DB, so the broker had no local
   metadata for cover devices and no fallback for channel creation.
4. **Library version mismatch (pre-existing):** the add-on pins
   `meross_iot==0.4.7.5`/paho 1.5.1; the HA component requires
   `meross_iot==0.4.9.2`/paho 2.x. The add-on should **not** be bumped blindly:
   its paho usage is 1.x. Cover support comes from the HA component’s library,
   not from the add-on’s pinned one.

## Fork

Path: ``.

Changed files:

- `rootfs/opt/custom_broker/model/db_models.py`
  - new `RollerShutterConfig` table (device, channel, signalOpen, signalClose,
    full payload JSON);
  - new `RollerShutterStatus` table (device, channel, position, state);
  - new `RollerShutterAdjust` table (device, channel, full adjust document);
  - new `DeviceAbility` table (device, ability JSON).
- `rootfs/opt/custom_broker/db_helper.py`
  - `set_roller_shutter_config()` / `get_roller_shutter_configs()`;
  - `set_roller_shutter_status()` / `get_roller_shutter_statuses()`;
  - `set_roller_shutter_adjust()` / `get_roller_shutter_adjusts()`;
  - `set_device_ability()` / `get_device_ability()`.
- `rootfs/opt/custom_broker/broker_agent.py`
  - observes app→device `Appliance.RollerShutter.Config` SET messages and
    persists them;
  - creates roller-shutter channel 0 from `System.All` digest, from the
    `Appliance.RollerShutter.State` ability, or from the MRS100 model type;
  - caches `Appliance.System.Ability`;
  - caches `Appliance.RollerShutter.Position/State` GETACK/PUSH notifications
    per channel;
  - caches `Appliance.RollerShutter.Adjust` GETACK/PUSH calibration results;
    Adjust SET is an operational command and is deliberately **not** replayed;
  - re-applies persisted timing config after `System.All`/reconnect, with a
    300 s cooldown and a disconnect-triggered reset;
  - ignores its own `/_agent` replay to avoid loops.
- `rootfs/opt/custom_broker/blueprints/device.py`
  - `devList` now includes a top-level `ability` object (the last
    `Appliance.System.Ability`) and, when present, a nested `rollerShutter`
    object with `config`, `position` and `adjust` arrays.
  - `HttpDeviceInfo`/the stock app tolerate the extra keys.
- `rootfs/opt/custom_broker/authentication.py`
  - Python 3 fix: `from _sha256 import sha256` → `from hashlib import md5, sha256`
    (the old import breaks any Python 3 import of the auth/blueprint stack).
- `rootfs/opt/custom_broker/s6.py`
  - removed the unused `from asyncore import read` import (removed in Python
    3.12; harmless on the bookworm base, but blocks newer Python builds/tests).
- `requirements.txt`
  - stays `meross_iot==0.4.7.5` (paho 1.x compatibility).
- `test_mrs100_roller_shutter.py` — 7 unit tests.

## Deployment

- The database tables are created by the existing `Base.metadata.create_all`
  on add-on start; no manual migration is needed.
- Build the add-on from the fork directory, or overlay the four changed files
  into an existing add-on image/container.
- Keep the upstream paho/meross_iot pins unless you also migrate the add-on to
  paho 2.x. The HA component remains on `meross_iot==0.4.9.2`.

## Validation on a real MRS100

1. Pair the device to the local broker (Custom Pairer or
   `Appliance.Config.Key` + `Appliance.Config.Wifi`).
2. Confirm the cover entity appears in HA (abilities include
   `Appliance.RollerShutter.State`).
3. Set open/close timings from HA.
4. Watch the add-on log for:
   - `Stored roller-shutter config for device ...`;
   - after reconnect/System.All: `Re-applied roller-shutter config ...`.
5. Re-read the config and verify it no longer falls back to 50 s.

## Next improvements

- Validate on a real MRS100 that the device accepts and persists the replayed
  `signalOpen`/`signalClose` object; the official app sends `payload.config`
  as an `MRSConfig` object, while `meross_iot` sends `{"config": {...}}`.
- If the device exposes multiple cover channels, extend the channel discovery
  to seed all `position`/`adjust` channels rather than only channel 0.
- Consider exposing `rollerShutter` metadata in the add-on Web UI, not only in
  the HTTP API.
- Add a local pairing helper for `Appliance.Config.Key`/Wifi if the Custom
  Pairer app is not desired.
- Keep the cloud out of the loop; only firmware catalog/metadata needs it.
